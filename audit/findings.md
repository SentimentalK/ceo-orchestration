# Findings

审计得到的事实记录。只在做 audit 或改规则时读；Conductor、Master、Worker 不读本文件。

本文件只追加。一条发现写：当时的配置、原先的预期、实际观察、证据、处置。日期、模型、数字都写在这里，不写进规则正文。规则因某条发现而改时，commit message 引用编号，并把该条的"处置"改成 commit。发现被后来的数据推翻时，不删，在该条下加一行"后续"。

不写用户原话和私有项目的细节；证据指向 `audit/reports/` 里的报告（不进 git）。

| 字段 | 内容 |
| --- | --- |
| 配置 | Conductor / Master / Worker 各用什么模型，规则版本（本仓库 commit） |
| 预期 | 规则或直觉原本认为会怎样；没有预期就写"无" |
| 观察 | 实际看到的，带分母 |
| 证据 | 报告路径和章节 |
| 处置 | 未处理 / 不处理（原因）/ commit |

## 2026-11-09 审计：LocalTune（11-04 → 11-09）

配置：Conductor 先是 Claude Fable 5.1（11-04），后是 deepseek-v4.1-flash（11-05 起）；Master、Worker 全程 deepseek-v4.1-flash，经 omp。规则版本 87e85ad → fc77227。约 70 张票，250 个派发。证据均在 `audit/reports/2026-11-09-localtune.md` 及同名目录下的底稿。

### F-001 Master 是否派 Worker 取决于 Spec 怎么写，和票大小无关

- 预期：票越小，Master 越倾向自己实现。
- 观察：自己实现的票中位 274 行，派 Worker 的中位 491 行，范围几乎重叠。派了 Worker 的 Master 按天是 13/13、10/13、14/14、14/22、0/10；转折点是 Conductor 的 Spec 从某张票起不再写"派 Worker"。
- 处置：7ed67fa（C3.8、R4.10、C5.8）。未在真实派发里验证。

### F-002 Orca 的派发 preamble 会让 Master 认定自己是 Worker

- 预期：Spec 指向 `roles/master.md`，身份门足以让它按 Master 行事。
- 观察：4 个 Master 的 Spec 明确要求派 Worker，仍自己写了代码；它们的推理引用了 preamble 里"你是被派发的 worker，自己完成本任务"。
- 处置：7ed67fa（master.md 身份门）。未在真实派发里验证。

### F-003 flash Worker 的完成报告是可信的

- 预期：小模型会虚报通过。
- 观察：115 个报告里的数字有 101 个能和工具输出对上，没有相矛盾的。107 个首次完成里 87 个跑了测试且最后一次全过，1 个测试失败但在正文里说明了。但 146 个 `worker_done` 全部报 `succeeded`，没有人用过 `--outcome failed`。
- 处置：7ed67fa（spec.md【结束】加 `--outcome failed`；报告可信这一点不需要处置）。未在真实派发里验证。

### F-004 Review 的形式成立，但挡不住行为错误

- 预期：Master 看 diff 并自己跑验收命令，就能拦住缺陷。
- 观察：144 次 Worker 完成后 137 次 Master 看了 diff 并跑了测试或构建。但 25 次 Worker 修补里 14 次是行为不对而测试没测出来，测试失败只有 2 次。用户纠正 Conductor 的 48 次里 26 次是交付了错的结果。有 2 张票的缺口写在 Master 自己的报告里，仍然关了。
- 处置：7ed67fa（C1.7、C5.7、R5.9）。未在真实派发里验证。

### F-005 换强模型当 Conductor，用户纠正的频率相近，类型不同

- 预期：Fable 当 Conductor 时用户介入明显更少。
- 观察：Fable 31 轮用户发言里 10 次纠正，flash 119 轮里 38 次。交付错结果 7 对 19，流程问题 2 对 11，误解 1 对 4，汇报不清 0 对 4。多数纠正是设计取舍，用户有意不事先说清。样本是一个项目，两段时间做的票不同，不是对照实验。
- 处置：7ed67fa（C1.7、C1.8；取舍类纠正不靠规则消除）。未在真实派发里验证。

### F-006 Spec 里的必写句随 Conductor 会话推进而消失

- 预期：规则写了"Spec 必须写一句…"，Conductor 每次都会写。
- 观察：第一个 flash Conductor 会话 10/10 份 Spec 带全部必写句，之后约一半，最后 14 份全没有。Master 和 Worker 只看 Spec，所以下游当天就变。
- 处置：7ed67fa（必写句移入 master.md R12；`tools/spec_check.py`）。未在真实派发里验证。

### F-007 记录类规则在后期不再执行

- 预期：无。
- 观察：决策记录 Fable 10 条、第一个 flash 会话 15 条、之后三个会话 0 条。没有验收段的票从 0/23 变成 10/22。Master 带 SHA 的写回 55/72，最后一天 0/10。`models.json` notes 最后一天 0/10。2 张票没有票文件。
- 处置：7ed67fa（`tools/ticket_check.py`、C6.1；决策记录仍靠 C2.4）。未在真实派发里验证。

### F-008 Conductor 实际承担了合并

- 预期：Master 集成，Conductor 不碰代码。
- 观察：最后一个 flash Conductor 会话跑了约 34 次 `git merge`，3 次替 Worker 提交工作区，2 次改源码解冲突。规则没有写 worktree 分支由谁合并。Fable 没有写产品代码。
- 处置：7ed67fa（C1.4、C4.11、R6.3）。未在真实派发里验证。

### F-009 agent 选了需要用户额外投入的方案，没有说明代价

- 预期：无。
- 观察：用户没有指定部署方式，agent 按业界惯例做了自动部署，需要用户给仓库配 token。用户的习惯是打 `latest` 后手动重启，没有理会，票挂了五天。
- 处置：7ed67fa（C1.6）。未在真实派发里验证。

### F-010 审计把"没有记录"写成了"没做"

- 预期：票和 transcript 足以判断遗留。
- 观察：遗留清单里 3 条经用户核对不成立。没有记录有三种可能：没做；用户在体系外做了、没告诉 agent；告诉了但没记下来。审计分不出这三种。
- 处置：`audit/README.md` 已加核对步骤。

### F-011 设计检查点从未打回过

- 预期：检查点能拦住有问题的设计。
- 观察：所有检查点的回复都是"同意"加补充，Fable 和 flash 都是。28 个 Master 用 `ask` 等了检查点。
- 处置：7ed67fa（C3.7）。未在真实派发里验证。

### F-012 部分规则在 omp 下执行不了

- 预期：无。
- 观察：`--effort high` 被 omp 拒绝；上下文交接和额度自查只有 Claude 的做法。第一次 omp 交接时新 session 退出了，Conductor 仍报成功。
- 处置：7ed67fa（模型 ID 改为引用 `models.json`；agent 专属做法单独成文）。未在真实派发里验证。
