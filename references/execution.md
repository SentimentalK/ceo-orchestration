# 执行、编排与恢复

只在创建 Run/Task、判断并行、放置 Worktree、选择模型、处理额度或未知状态、返工、更新 Ticket、核验 Git/CI 时读取本文件。命令和字段以本机已安装的 orchestration 紧凑手册为准；命中 `SKILL.md` 的官方动作门禁时，再加载那一个官方 Reference。

本文件不复制命令手册。这里的策略比 Orca 安全底线更严的部分仍然有效。

## 调度边界

- Orca Run 是耐久命名空间和收件箱，不负责替你调度。Task 是工作。Dispatch 是一次权威尝试。
- 复用 Orca 的 Run、Task、Worker、Gate、Worktree。不要自建 Scheduler、Provider Router、数据库或第二套任务状态机。
- 一个执行阶段绑定一个 Run。恢复时只读巡检已有 Run、Task、Worker 和收件箱，再决定是否 `run-use`。不要为了绕过失败而新建 Run。
- 活跃协调期间不要执行破坏性的 orchestration reset，除非调用者明确放弃该状态。
- 普通运行期提问用 Worker 的 `ask` 和你的 `reply`。不要为了回答普通提问创建 Gate。
- Gate 只用于阻断下游 Task，等待一个真正的放行决定。改变技术路线、业务语义或验收标准的决定不能由你 `gate-resolve`。这种 Gate 只负责保持阻断，决策等待上层。
- 合法的 `worker_done` 会结算 Task 和 Dispatch。不要再补一次把 Task 标完成的写操作。

## 依赖与并行

只为真实顺序设置依赖。优先宽而浅的并行波次，避免超过三到四层的深链。嵌套 Worker 受运行时深度上限约束；新建 Run 不会重置深度。

允许同一波次并行：

- 都是只读 Research、审计或 Review，且不修改同一工作区的构建产物或生成文件。
- 接口契约已经冻结，允许修改的文件集合互不相交，并且并发写入放在隔离 Worktree 中。

禁止并行：

- 两个 Worker 的写入范围相交，包括生成文件、锁文件和同一测试产物目录。
- 后一个任务消费前一个任务尚未冻结的接口。
- 高成本实现依赖尚未完成的有界 Research，或依赖尚未放行的 Gate。

并发写入必须同时具备隔离 Worktree 和写明的集成策略：谁集成、按什么顺序、冲突时谁停止。各分支先独立 Review，再集成；集成后在集成工作区重跑约定验证。放置参数在真正新建或指定 Worktree 时加载官方 `references/placement-and-remote.md`，不要凭记忆拼 flag。

同一工作区可以串行执行，也可以跑只读并发。这是默认放置。不要为了只读任务复制仓库。

## Worker 派发

- Spec 必须满足 [`contracts/task-spec.md`](contracts/task-spec.md)。注入正文使用 [`templates/worker-prompt.md`](templates/worker-prompt.md)。
- 按任务复杂度和成本选择 Coding、Research 或 Review Agent。只使用调用者授权且本机真实可用的 Agent。不要把某次会话的模型、订阅或机器配置当成通用前提。
- 调用者精确指定模型时，不得暗中更换 Agent 或模型。官方手册不允许在该放置上覆盖模型时，改用不改变模型的已支持放置，或停止并报告。不要换成未授权 Agent 冒充。
- 未指定模型时，省略模型参数，让 Worker 继承该 Agent 的既有配置。只有该模型支持时才传 effort。
- 启动收据返回后，核对请求身份和生效身份。只凭请求参数，不得声称目标模型已经运行。
- `worker-start` 非零退出时不要立即再启动。先看失败阶段和残留资源，再加载官方 `references/recovery-and-cleanup.md`。

## 完成不等于验收

Worker 报告成功，只说明这次尝试已结算，不说明业务验收通过。验收规则在 [`contracts/review-rubric.md`](contracts/review-rubric.md)。

每个已结算且你有权处置的终端，在确认收件箱批次之前三选一：同终端复用、调用者要求的显式保留、或释放。不要为了查看输出而把终端留着；已归档输出仍可只读查看。结束本轮前，可回收终端必须清点完毕。

Review-only 的结算只授权你汇总发现并派发修复。不授权 Reviewer 或你在审查环节直接改业务文件。调用者明确把编码指派给你时除外。

收件箱按批次先处理、后确认。处理完提问、核对 `worker_done` 的 Dispatch，并决定每个已结算终端的下一归属，再确认该批次。

## 安全恢复

命中失败、已停止或结果未知的尝试，或重试、停止、放弃、保留请求，或不确定释放时，加载官方 `references/recovery-and-cleanup.md`，并遵守：

- 状态变更命令只执行一次。响应丢失时先只读核查该请求和实际 Run、Task、Dispatch。已完成的不再发。仍在进行的按原请求身份接合。无收据不是“什么都没发生”。
- `check` 超时或空结果是检查点，不是失败，也不是死亡。
- 连续空等待后停止盲等，改为带 Run 范围的只读枚举。Agent 存活以舰队裁决为准；终端进程存活不等于 Agent 存活。二者冲突时，先按官方恢复文档判断哪一侧有正向证据。
- `unverifiable` 和缺席不是退出。没有正向退出证据前，不得 stop、abandon、retry 或 release。
- 只有已证实 `failed` 或 `stopped` 的尝试才能对同一 Task 重试。重试必须指向旧尝试，并显式重复放置。不得用 `--spec` 另建一个重复 Task。
- 同一 Task 连续启动失败触发 Orca 熔断后，停止并汇报。不得用新 Run、新 Task 或其他 Dispatch 绕过。
- Worker 状态未知时不得盲目重试。先只读核查；需要隔离时，在官方文档允许的正向证据下显式 stop 或 abandon。
- 已结算、被用户接管、复用中的既有终端，或你无权控制的 Worker，不得擅自重启或释放。
- 释放只发生在已接受的结算之后。超时、空闲、心跳、提问、升级和过期完成都不是释放理由。释放结果不确定时，执行收据给出的恢复动作，不要改用关闭终端代替。

## 额度切换

只有同时满足以下条件才允许模型 Failover：

1. 调用者事先明确授权了备选模型。
2. 容量失败有实证，不是超时或空收件箱。
3. 原 Worker 已经证实安全停止，不会继续写文件。

否则等待配额恢复，或停止并报告。精确指定的模型不适用这条切换。

Worker 遇到额度耗尽时，必须如实上报失败或升级。不得静默退出，不得编造输出。

## 预算、重试与时间

遵守调用者给出的重试次数、预算和执行时间上限。调用者没给数字时，不要发明无限运行，也不要发明一套新的配额服务。Orca 熔断、授权预算耗尽、或继续执行会超过已声明的时间上限时，停止并汇报。

并发度不超过已证实可隔离的写入范围，也不超过调用者的预算。不要按某台机器的 CPU 或订阅档位写死并发数。

## Git、CI 与 Ticket

Git 和 CI 是交付证据，不是叙事。

- 交付前核对工作区：只含授权文件，没有调试垃圾、密钥或其他仓库的改动。
- 调用者授权提交时，使用清晰的 Conventional Commit。不要加未经请求的 AI Co-author。不要 `--force`，不要跳过 Hook。
- 授权推送时，只做常规 fast-forward，并核对本地 HEAD 与远端跟踪分支是同一 SHA。
- 仓库配置了 CI 时，证据必须是该精确 SHA 的终端成功。失败则在授权范围内返工。仓库没有 CI 时写明没有，不要编造绿色运行。
- 没有足够证据不得把 Ticket 标为 DONE。Worker 完成、测试变绿、Reviewer 建议通过，每一项单独都不够。

CEO Ticket 只有启动契约中的单一 Writer 通道可以写。Worker 不得写 Ticket 状态。你只更新本轮授权执行且已经按审查规则验收的 Ticket。没有通道时，只在交接汇报里给出建议状态和证据。
