# 独立 Review 与验收

安排独立 Review、做验收裁决或生成返工清单时读取。恢复和派发动作遵守 [`../execution.md`](../execution.md)，不在这里重复命令。

实施者不得为自己的交付做最终验收。非平凡设计或代码由独立高能力模型审查。审查者只读；审查报告可以写到 Spec 指定的报告路径。

Reviewer 的 `ACCEPTED` 只是建议。你必须对照实际 Diff、测试、CI 和任务约定的其他客观证据后再验收。缺少证据就不得验收，也不得标 DONE。

Review-only 结算只授权汇总发现和派发修复。不授权 Reviewer 或你在审查时改业务文件。调用者明确把编码指派给你时除外。

## 四项核查

任一项有致命缺陷，不得验收。

### 1. 契约与范围

- Spec 要求的行为、接口、产物和文档已实现，不是空壳或未接上的桩。
- `git status` 与 `git diff` 只碰 Ownership 白名单，没有触碰 Do-Not-Touch。
- 没有改未授权仓库，没有未授权依赖，没有密钥或凭据。

### 2. 正确性与诚实性

测试变绿不能抵消这一项。

- 行为符合已批准的契约，而不是只迎合测试形状。
- 没有把预期答案、隔离数据或评测真值写进被测实现。任务若定义了数据隔离，按该契约检查，不套用其他项目的评测方法。
- 证据不足时按契约失败关闭或标未知，没有伪造完整结果。
- 指标、日志、SHA 和 CI 结论来自实际命令。无法复现的数字视为失败。
- 没有为了通过而放宽验收、跳过测试或删除失败用例。

### 3. 测试与可证伪性

- 约定的既有测试仍然通过，没有用跳过或删改掩盖。
- 本次缺陷有回归：旧实现会失败，修复后通过。
- 断言检查任务要求的可观察行为。

### 4. Git、CI 与可复现证据

- 工作区没有授权范围外的脏文件。
- 授权提交时，历史清晰，没有 force push，没有未经请求的 AI Co-author。
- 授权推送时，本地 HEAD 与远端是同一 SHA。
- 仓库有 CI 时，该精确 SHA 的运行已成功。没有 CI 就写明没有。禁止编造绿色运行。

## 裁决

Reviewer 在报告中给出一个建议裁决。你独立核验证据后，才把它变成验收决定。

| 建议 | 标准 | 你的动作 |
| --- | --- | --- |
| `ACCEPTED` | 四项都有客观证据，且没有放宽上层验收。 | 你复核 Diff、测试和 CI 后才验收。然后按 [`../execution.md`](../execution.md) 处置终端、集成隔离分支，并只通过单一 Writer 通道更新已授权 Ticket。 |
| `REWORK` | 缺陷在当前详细设计和批准约束内可修复。 | 把缺陷写成有界修复 Spec，包含失败复现测试。派发修复，修完重新 Review。 |
| `ESCALATE` | 必须改变上层路线、业务语义或验收；钉死的模型不可用且不能 Failover；熔断、预算或时间上限已到；需要未授权 Ticket 或仓库。 | 停止自动推进，保留证据，向上层汇报根因、影响和建议选项。不要自行放行。 |
